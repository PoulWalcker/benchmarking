# Pinned task environment interface

The first integration uses AutoWFBench Production Checkout Recovery at
`970bbc8645c4d503d35cb5df05363fb9de132519`. The Sapiens specification pin is
unchanged. This module provides trusted source verification and a fresh original
simulator for each attempt; it neither solves the task nor calculates a score.
See [the source investigation](history/RESEARCH-AUTOWFBENCH.md) for the case and rubric.

## Source dependency

`sapi_config_lab.execute.autowfbench` reads the installed adjacent
`autowfbench-source.json`. It records the upstream commit and SHA-256 of every
tracked file. No upstream source is copied into the distributed lab package.
The local ignored cache contains the original source, including evaluator files;
it belongs to the trusted orchestrator and must not be mounted into a solver.
The inspected upstream tree declares no license file. A public manifest and
local fetch do not assert permission to redistribute upstream code.

- `fetch_source(cache_root) -> Path`: explicit network operation, fetching the
  exact pinned raw URLs into a temporary directory. Every hash must match before
  the commit directory is published. An existing cache is verified, never
  silently repaired or upgraded. A `fetch` callable can supply bytes for tests.
- `verify_source(source_root) -> dict`: fully offline integrity check. Rejects
  changed/missing files, symlink source files and extra files that could alter
  imports. Returns repository, revision, file digests and manifest digest.
- Original upstream imports require the `benchmark` dependency extra. The
  integration uses `fastjsonschema==2.22.2` through the shared lockfile.
  Set `PYTHONDONTWRITEBYTECODE=1` when another trusted module imports the cached
  dependency: generated bytecode is intentionally not part of the closed cache.

For an explicitly authorized first fetch:

```python
from pathlib import Path
from sapi_config_lab.execute.autowfbench import fetch_source, verify_source

source = fetch_source(Path(".cache/autowfbench"))
pin = verify_source(source)
```

Normal compilation, verification and environment startup do not fetch sources.
The cache is disposable; results must preserve the source-manifest digest and
upstream revision separately from its machine-specific path.

## Trusted lifecycle

```python
from sapi_config_lab.execute.autowfbench import start_environment

with start_environment(source, seed=0) as session:
    definition = session.definition
    candidate_connection = session.connection
    # The orchestrator admits and times the candidate, passing only the public
    # definition and candidate connection. The candidate calls /tools.
    evidence = session.finalize()
```

`start_environment(source_root, challenge_id="production-checkout-recovery",
seed=0, *, python=sys.executable, bind_host="127.0.0.1",
public_host="127.0.0.1")` verifies source before launching the unchanged upstream
environment command. It waits for the child readiness message before returning.
Each session starts from original fixtures, with independently generated tokens
and fresh process-local state. Starting another session is the reset operation;
there is no solver-accessible reset method.

The trusted interface exposes:

| Member | Meaning |
| --- | --- |
| `definition` | Original public task, capability names, completion instruction and limits |
| `connection` | Copy of `{base_url, access_token}` for this candidate only |
| `call(operation, arguments={}, *, operation_id=None, max_attempts=1)` | Same original tool interface; optional explicitly bounded transport retry and receipt replay, never task decisions |
| `finalize()` | Freezes calls and returns original `{initial, final, events, verification, checks, tool_calls}`; repeated calls return independent copies of the same frozen evidence |
| `transport_evidence()` | Separate project-policy events, attempt counts and ambiguity status; never changes original verification evidence |
| `close()` | Stops proxy and child; idempotent and called by the context manager |

Only the trusted scorer/orchestrator receives finalization evidence. It builds
the run log with candidate output separately labeled; candidate trace entries
cannot replace environment or verification records.

The original 120-second candidate timer is the orchestrator's responsibility.
Upstream starts this timer after environment provisioning, immediately before
dispatching the candidate's `/runs` request, and stops it when terminal submission
is received. Setup and judging are excluded. If a candidate authors YAML after
admission, authoring and compilation consume the same 120 seconds. If a version
is authored/frozen beforehand, its authoring time is a separate recorded phase;
do not call the later runtime duration end-to-end task time. Finalize on timeout
before cancellation/judging, preserving partial authoritative evidence.

## Candidate tools

The proxy accepts only `POST /tools` authenticated by
`Authorization: Bearer <access_token>` with the exact JSON object
`{operation: string, arguments: object}`, with optional `operation_id` and
`max_attempts`. URL and credentials come from trusted
execution configuration, not from model-authored tool arguments.

| Registered upstream operation | Arguments | Successful value |
| --- | --- | --- |
| `incident.read` | `{}` | Incident facts, deployment information and patch restrictions |
| `source.read` | `{}` | `{path, content}` |
| `checkout.patch` | `{old: string, new: string}` | `{updated}` after original AST validation |
| `tests.run` | `{}` | `{passed, cases}` from the original public tests |

Successful calls return `{ok: true, value: ...}`. Tool errors retain HTTP 200
and `{ok: false, error: {code, message, retryable}}`; they are observations the
workflow may inspect, not transport retries or automatic repairs. The original
simulator controls tool-call accounting, capability admission, patch restrictions
and final verification. Unknown operations remain original recorded failures.
Malformed proxy requests fail before a tool invocation; they are protocol errors.

`/admin/finalize`, `/state`, `/evaluate` and every other route return 404 on the
candidate listener, even with valid candidate credentials. Each candidate token
is distinct from original run/admin tokens and other sessions' candidate tokens.
After finalization, tool calls return `RUN_CLOSED` without mutating frozen state.
No grading answer or known patch is implemented in this module.

## CRM and run-scoped receipt policy

The same pinned environment supports `crm-lead-qualification`, using a fresh
process per attempt. Its eight original tools are:

| Operation | Arguments |
| --- | --- |
| `inquiry.read`, `documents.read`, `research.read`, `crm.read` | `{}` |
| `customer.ask` | `{questions: string[]}` |
| `crm.update` | `{changes: object}` with only original writable lead fields |
| `followup.create` | `{lead_id, type, status}` |
| `customer.send` | `{recipient, body}` |

The following **project transport policy** sits outside the original simulator
and scorecard. Its evidence is separately labelled
`sapi-lab-run-scoped-receipts/v1`; original checks and call accounting remain
unchanged. The default is one dispatch. An explicitly configured `max_attempts`
of 2 or 3 requires an operation ID and retries only a received original error
with `retryable=true`. In these two pinned simulators, the transient CRM update
failure occurs before mutation. A nonretryable result stops immediately. Every
actual retry appears in the original environment trace and consumes its budget.

Operation IDs are scoped to one live session and limited to 240 characters.
Before dispatch the proxy reserves the ID with a canonical digest of operation,
arguments and attempt policy. Reusing the same ID/request returns the saved
receipt without another tool call; changing its arguments or policy returns
`PROJECT_OPERATION_ID_CONFLICT`. Compiler-generated IDs include logical step and
native workflow/execution identity. This deduplicates delivery of the same
operation; distinct workflow steps remain distinct operations, even with equal
arguments.

Two kinds of lost response are deliberately different:

- If the proxy saved a receipt but its response to the client was lost, replaying
  the same operation ID is safe and returns that receipt.
- If upstream might have committed but the proxy did not receive a valid receipt,
  the result is `PROJECT_AMBIGUOUS_OUTCOME`, with `retryable=false`. Further
  dispatch in that session stops, including attempts with a new ID. The trusted
  orchestrator can still finalize/read authoritative evidence. The proxy never
  assumes the action had no effect or blindly retries creation/sending.

The ledger is in memory and survives neither process loss nor a new session.
This is not durable or universal exactly-once execution, and it does not detect
semantically equivalent duplicate actions assigned different IDs. These bounded
guarantees apply to the two supported synthetic simulators, not arbitrary real
CRM/payment providers. A new session resets both original state and receipts.

For Docker candidates, the trusted host may explicitly select
`bind_host="0.0.0.0", public_host="host.docker.internal"`. Only the candidate
proxy becomes reachable that way; the upstream administrative listener remains
loopback. Keep the trusted host and source cache outside the solver container.
Process separation alone is not protection from malicious code running as the
same operating-system user. Tokens are run-scoped secrets and must be excluded
from public workflow exports, prompts, logs and reports.

## Controls and validation

`tests/support/checkout_controls.py` contains explicitly labeled oracle and
incomplete action sequences. They are verifier controls, not model solutions,
and must not be included in solver task packages or generation instructions.
The candidate-facing module contains no golden patch.

`tests/test_autowfbench_environment.py` exercises unchanged upstream child
processes over actual loopback HTTP: before/after effects, original final checks,
fresh reset, cross-session token rejection, absent administrative routes, tool
budget, rejected arbitrary Python, freeze, cleanup and source mutation rejection.
Source-cache tests run without the dependency checkout; genuine simulator tests
are explicitly skipped if the pinned cache is absent. Set
`SAPI_AUTOWFBENCH_SOURCE` to an existing verified checkout when it is elsewhere.
Tests do not fetch automatically and never call a model, Docker or real payment
service.

```sh
uv run --locked --extra benchmark python -m unittest tests.test_autowfbench_environment -v
```

The initial checkout validation passed nine tests against the pinned original
simulator. The sandbox initially denied loopback binding; the authorized local
test command succeeded with the tool's approval for that local listener.
This is deterministic environment-interface evidence, not n8n integration or
an LLM quality result.

The CRM extension passed fourteen environment/cache tests, including original
CRM qualification with explicit transient retry, both lost-response windows,
repeated/conflicting keys, nonretryable rejection, attempt limits, and reset of
state/failure budget/receipts in another session. No model or real CRM call was
used for those controls.
