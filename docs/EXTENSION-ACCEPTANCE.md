# Independent extension acceptance

`verification/extensions.py` does not import the compiler, controller, or business operation implementations. It checks the declared business contract separately from native execution provenance. Its synthetic unit fixtures exercise rejection behavior; they do not establish that n8n ran.

## Reply refinement (04)

`verify_refinement(config, run, mode="live")` checks the two-operation reply task in one native n8n execution. It independently applies the required order-ID and UTF-16 character-limit rules to each real draft. Every later attempt must consume the actual previous draft and review errors. An accepted attempt stops the graph; exhausting the configured maximum must produce a native failure and no accepted output.

The verifier binds each logical attempt to its native Fixture, operation, Checkpoint, and continuation branch records. It checks native source channels and timing, preserved input and runtime lineage, one shared deadline, the accepted revision, and the absence of unexecuted or unexpected nodes. For live drafts it also checks Prepare/Guard/Agency/Restore records and invocation IDs containing the attempt number and the same native workflow/execution identity. Checkpoint summaries and adapter status flags alone cannot establish acceptance.

The returned `calls` list must additionally be reconciled against the independently persisted Agency admission, wrapper-attempt, and completion audit by the experiment runner. These content/provenance checks alone do not prove how many external calls were charged, transport reliability, or the factual quality of natural-language replies beyond the declared mechanical review rule. Independent qualitative agent review is recorded separately from human review.

The compiler supports a broader bounded whole-DAG refinement form. This business verifier deliberately covers the declared reply task only; other refinement business tasks require separately stated acceptance predicates. Technical failures before a complete checkpoint are not accepted as successful exhaustion.

The existing generation command admits `--scenario revise-answer --attempts 3 --series-dir NEW_DIRECTORY`. It runs fresh unpaid Harbor controls first, then reserves each one-shot authoring separately. The separate `sapi-lab-refinement-series/v1` ledger permits three authoring calls and reserves up to three runtime calls for each of `valid-reply` and `impossible-limit`. It cannot reopen an expansion ledger or continue after a failed/unknown reservation. Baseline and four-scenario expansion defaults are unchanged.

The normal reply case requires the order ID A7842 within 280 UTF-16 units. The exhaustion case uses the same input and a one-unit limit: no string containing that five-character ID can pass. This tests declared failure behavior; it is not described as an accepted reply. Both fixture cases are frozen before authoring. A live run may accept its first attempt; evidence must not claim a rejection-and-correction sequence unless it actually occurred.

`python -m sapi_config_lab.experiments.replay --scenario revise-answer --source-report GENERATION/report.json --output SELECTION.json` selects the chronologically first original YAML only after all three independently authored submissions pass their stub controls. The existing live runner accepts `--scenario revise-answer --series-dir SERIES --submissions-manifest SELECTION.json --stub-report GENERATION/control/report.json --wrapper-evidence IDENTITY.json --report-dir NEW_LIVE_DIRECTORY`. It preserves original YAML bytes and discloses fixture-input and 600-second deadline overlays. The series ledger records reserved upper bounds; native/Agency/wrapper evidence records actual attempts, which may be fewer than six. No authoring repair, transport retry, or handwritten replacement is admitted.

## Lifecycle (05)

Lifecycle admission and revision transitions belong to an explicit external controller. The imported native graph represents one admitted digest run; it must not be presented as executing Cron scheduling, fork persistence, or lifecycle transitions itself. Independent lifecycle evidence checks are developed against the durable controller event and definition records, together with each event's native execution evidence.

`verification.lifecycle.verify_lifecycle(snapshot, mode="live")` checks the completed digest lifecycle independently of the controller implementation. It verifies definition hashes, deduplicated event identities, native input/output lineage, the exact tested release, feedback-to-fork identity, persistence before archive, new Callback testing, rebuild caps, final revision states, suspension/Adhoc records, and restore-without-replay. A mock backend or a controller-only success record fails native provenance. A rejected digest that completed natively can drive a real rebuild; its rejected output remains visible. The default real-Cron check requires system-clock admission at the declared local minute. An explicitly injected test clock is useful for deterministic controls but does not establish wall-clock scheduling.

The returned native calls still need wrapper audit reconciliation. Rebuild model authorship is deliberately reported as unverified by the snapshot checker: the experiment must separately compare each rebuild's reserved source/findings/target, prompt, original candidate bytes, wrapper dispatch/completion and installed candidate hash. Operator-registered forks must retain their distinct origin and cannot establish model rebuilding. The snapshot checker does not prove transactional crash behavior from a final snapshot alone; restart, deduplication, uncertain-outcome and overlap controls provide that additional evidence. It also does not claim factual completeness of natural-language summaries merely because preview shape and source IDs pass.
