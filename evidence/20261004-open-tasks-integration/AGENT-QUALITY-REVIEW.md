The SC-03/SC-04 briefs contain no apparent filler. Digest text repeated in the final brief and copied evidence is structural duplication required by these outputs; removing it from preserved evidence would be inappropriate. Their material is extremely short, however, so these results establish faithful compact restatement on these fixtures, not synthesis skill on complex documents.

SC-02 demonstrates **honest detection of an overlong draft**, not a successful concise customer answer. This is successful execution of its declared one-shot review-packet task, which explicitly permits a failed draft review; it is not an execution bug. The high/normal replies contain 205/237 UTF-16 code units against the 120-unit limit. The catalog's `reply.generate` input has no length-limit field; it receives only projected ticket data, previous text, and feedback. The model therefore is not directly given the runtime `max_characters` constraint in the initial draft call. Blaming this entirely on model verbosity would miss the missing constraint in its interface.

If a future task requires an accepted concise answer rather than an honest one-shot review, a generic correction for the owner to assess in a separately frozen change is to convey the actual review constraints to initial drafting through an explicit supported interface or constraint-bearing feedback, and make the common drafting instruction request one short, actionable sentence without unverified action claims. If feedback remains empty by task design, retain the honest rejection and use the planned bounded revision mechanism to consume the actual check errors. Do not patch individual recorded replies or hard-code these fixture IDs. A new style instruction alone cannot guarantee an undisclosed per-case length limit.

No content correction is requested for the three reviewed research briefs. For the two support replies, preserve `pass: false` and do not present them as ready-to-send messages. Any future UI should make that review result visible alongside the draft.
